# Concheron SEC System --- Technical Architecture & Design Specification

**Version:** 1.0\
**Status:** Proposed technical design based on approved application
requirements\
**Target subsidiary platform:** PHP 7.4, Zend Framework 1, DHTMLX 3.5,
MariaDB, Apache\
**Staff certificate mode:** Mode A --- authentication and authorization
only

------------------------------------------------------------------------

## 1. Design Objectives

The system must provide secure SEC document distribution from Concheron
to subsidiaries while maintaining distinct cryptographic and
authorization boundaries.

The design has five principal controls:

1.  **Private VPN + SEC USB** controls access to the central Concheron
    SEC portal.
2.  **Per-USB package encryption** controls possession and initial
    import of downloaded SEC packages.
3.  **Subsidiary server encryption** protects imported original PDFs at
    rest.
4.  **Staff certificates (Mode A)** authenticate staff and participate
    in authorization, but do not decrypt documents.
5.  **Server-side rendering + watermarking** prevents the browser from
    receiving the original PDF during normal viewing.

## 3. PKI Architecture

### 3.1 Recommended Hierarchy

``` text
Concheron Root CA
|
+-- Concheron USB Issuing CA
|   +-- SEC USB A-001
|   +-- SEC USB A-002
|   +-- SEC USB B-001
|
+-- Concheron Staff Issuing CA
|   +-- Staff Certificate A-1001
|   +-- Staff Certificate A-1002
|
+-- Concheron Server Issuing CA
|   +-- Company A Server Certificate
|   +-- Company B Server Certificate
|
+-- Concheron SEC Package Signing Certificate
```

The offline Root CA should not routinely perform operational signing.
Separate issuing/signing keys limit the impact of compromise.

### 3.2 Certificate Purposes

USB certificates identify SEC USB credentials and support
challenge-response plus package-key wrapping.

Staff certificates identify staff members and support Mode-A
authentication.

Server certificates/keys identify and protect subsidiary server
cryptographic operations.

The SEC package-signing certificate signs packages generated by
Concheron.

Certificate key-usage and extended-key-usage policy should prevent
credentials intended for one purpose from silently being reused for
another.

### 3.3 Certificate Identity Fields

Concheron should assign immutable internal identifiers rather than
relying on display names.

Example logical identity:

``` text
Certificate Type: STAFF
Certificate ID: CERT-STF-A-001004
Staff ID: EMP-A-0041
Company ID: COMPANY-A
Issuer: Concheron Staff Issuing CA
Serial: <unique serial>
```

Certificate lifetimes are configurable Concheron policy.

## 4. SEC USB Architecture

### 4.1 Required Properties

Each SEC USB credential should provide:

-   Unique device identity.
-   X.509 certificate or equivalent approved credential.
-   Public/private key pair.
-   PIN/password protection.
-   Private-key operations after successful unlock.
-   Preferably non-exportable private key storage.
-   Device/certificate serial number.
-   Assigned subsidiary and SEC staff mapping.

A hardware cryptographic token is preferred to a normal mass-storage USB
device.

### 4.2 Portal Authentication Protocol

``` text
1. User establishes private VPN connection.
2. User authenticates normal portal account.
3. Portal requests SEC USB authentication.
4. Server generates cryptographically random challenge.
5. User unlocks USB with PIN/password.
6. USB signs challenge using its private key.
7. Portal validates certificate chain/status/policy.
8. Portal verifies challenge signature.
9. Portal maps USB identity to user and subsidiary.
10. Portal establishes SEC-authenticated session.
```

The challenge must be single-use and short-lived to prevent replay.

### 4.3 USB Authentication State

The server should record a server-side authentication state containing:

``` text
user_id
usb_certificate_id
company_id
challenge_id
authenticated_at
expires_at
session_binding
```

The USB PIN must never be stored by the application.

## 5. SEC Package Cryptographic Design

### 5.1 Envelope Encryption

Each download generates a fresh random content-encryption key (CEK).

``` text
PDF bytes
   |
   | fresh random CEK
   v
AES-256-GCM
   |
   +--> ciphertext
   +--> authentication tag
```

The CEK is wrapped for the authenticated SEC USB public key using an
approved public-key encryption/key-encapsulation mechanism compatible
with the chosen USB token.

The exact asymmetric mechanism must be selected according to the
token/key type and approved cryptographic library. It must not be
invented as a custom algorithm.

### 5.2 Package Components

Logical package structure:

``` text
SEC Package
|
+-- Header
|   +-- magic/version
|
+-- Manifest
|   +-- package_id
|   +-- document_id
|   +-- document_version
|   +-- classification
|   +-- target_company_id
|   +-- recipient_usb_certificate_id
|   +-- created_at
|   +-- optional expires_at
|   +-- crypto_suite_id
|
+-- Encrypted Content
|   +-- ciphertext
|   +-- nonce/IV
|   +-- authentication tag
|
+-- Recipient Data
|   +-- wrapped CEK
|   +-- recipient key/certificate identifier
|
+-- Integrity Metadata
|
+-- Concheron Digital Signature
```

The physical encoding may be binary rather than ZIP. Subsidiaries should
interact with it through the Concheron extension.

### 5.3 Authenticated Data

Security-critical metadata such as package ID, document ID/version,
target subsidiary, recipient identity, and crypto-suite version should
be cryptographically bound to the encrypted content using authenticated
data and/or the package signature.

An attacker must not be able to change the target subsidiary or document
identity without verification failure.

### 5.4 Package Signature

Concheron signs the complete security-relevant package representation.

Verification occurs before the imported document is accepted.

The implementation must define a canonical serialization so the exact
signed bytes are unambiguous.

## 6. Package Identifiers and Replay Protection

Each generated download receives a globally unique package ID.

Example:

``` text
PKG-2026-09-27-<random identifier>
```

The subsidiary stores previously processed package IDs and cryptographic
hashes.

Import logic should classify a package as:

-   New package.
-   Authorized new document version.
-   Exact duplicate.
-   Replay.
-   Unsupported/older version.
-   Invalid/tampered package.

Downgrade policy must be explicitly enforced.

## 7. Concheron PHP Extension Architecture

### 7.1 Boundary

``` text
ZF1/PHP Application
        |
        | high-level API
        v
php_concheron_sec.dll / concheron_sec.so
        |
        +-- Package Parser
        +-- Signature Validator
        +-- Certificate Validator
        +-- USB Adapter
        +-- Crypto Provider
        +-- Server-Key Adapter
        +-- Secure Temporary Processing
```

The extension should be implemented in C/C++ using an approved mature
cryptographic library and appropriate USB-token interface.

### 7.2 API Philosophy

Expose business operations rather than raw cryptographic primitives.

Recommended conceptual API:

``` php
concheron_sec_version();

concheron_sec_inspect_package($packagePath);

concheron_sec_verify_package($packagePath);

concheron_sec_import_package($packagePath, $options);

concheron_sec_verify_staff_certificate($certificateContext);

concheron_sec_open_document($documentReference);

concheron_sec_close_document($handle);
```

The exact PHP API will be finalized during extension design.

Avoid APIs such as:

``` php
get_private_key();
get_raw_document_key();
export_server_key();
```

### 7.3 Extension Result Model

Functions should return structured status information:

``` text
success
error_code
operation_id
safe_message
metadata
```

Sensitive internal cryptographic details must not be returned to normal
PHP responses.

### 7.4 Extension Versioning

The extension exposes:

``` php
concheron_sec_version();
```

The ZF1 application checks the installed version against a minimum
supported version.

## 8. Subsidiary Import Architecture

### 8.1 Import Sequence

``` text
Upload .sec
   |
Authenticate SEC manager
   |
Require/import USB credential
   |
Verify package structure/version
   |
Verify Concheron signature
   |
Verify target subsidiary
   |
Verify recipient USB
   |
USB PIN/private-key operation
   |
Unwrap CEK
   |
Authenticate/decrypt AES-GCM content
   |
Validate document metadata/hash
   |
Create controlled plaintext processing context
   |
+---------------------------+
|                           |
v                           v
Render pages          Re-encrypt original
                          |
                     Server-side key
                          |
                          v
                 Encrypted master PDF
```

### 8.2 Transactional Import

The application creates a pending import record first.

Only after all required operations succeed should the document become
`ACTIVE`.

Example states:

``` text
UPLOADED
VERIFYING
DECRYPTING
PROCESSING
COMMITTING
ACTIVE
FAILED
```

A failure must trigger cleanup of temporary plaintext and incomplete
artifacts.

## 9. Server-Side Re-Encryption

### 9.1 Storage Encryption Model

The imported PDF is encrypted with a server-controlled storage key.

A recommended design uses envelope encryption again:

``` text
Imported PDF
    |
fresh per-document data key
    |
AES-256-GCM
    |
Encrypted master PDF
    |
data key protected by subsidiary server key
```

This is preferable to encrypting every large PDF directly with an
asymmetric server private key.

### 9.2 Storage Metadata

Store:

``` text
storage_key_id
crypto_suite_id
encrypted_file_path
nonce/IV
authentication metadata
encrypted/wrapped data key
encrypted_file_hash
```

No plaintext PDF should be retained as the permanent master.

### 9.3 Key Rotation

A key registry should support:

``` text
KEY-A-001  RETIRED
KEY-A-002  ACTIVE
KEY-A-003  FUTURE
```

Rotation may re-wrap per-document data keys without necessarily
re-encrypting every large PDF, depending on the final key hierarchy.

------------------------------------------------------------------------

## 10. Server Key Storage

The server key must be protected independently from document storage.

Preferred options, in descending assurance depending on available
infrastructure, include:

1.  HSM or hardware-backed key store.
2.  OS/platform protected key store.
3.  Strongly protected encrypted key store with restricted service
    identity.

The web application's database must not contain an unprotected server
private key.

Backup and disaster-recovery copies must be protected at least as
strongly as production keys.

------------------------------------------------------------------------

## 11. Staff Certificate Architecture --- Mode A

### 11.1 Selected Role

Staff certificates are used only for:

-   Authentication.
-   Identity binding.
-   Authorization input.
-   Audit attribution.

They do **not** decrypt SEC document content or storage keys.

### 11.2 Staff Verification Sequence

``` text
Application Login
       |
Staff certificate requested
       |
Validate certificate chain
       |
Validate signature/policy
       |
Check validity period
       |
Check revocation/status
       |
Verify Company ID
       |
Challenge-response/private-key proof
       |
Map certificate to staff account
       |
Check account/SEC permissions
       |
Certificate-authenticated session
```

### 11.3 Authorization

After certificate authentication:

``` text
Authenticated Staff
       |
       +-- Account active?
       +-- SEC access enabled?
       +-- Correct subsidiary?
       +-- Classification permitted?
       +-- Document permitted?
       +-- Access period valid?
       |
       v
ALLOW / DENY
```

Certificate validity and document authorization remain separate
decisions.

------------------------------------------------------------------------

## 12. Revocation in Isolated Subsidiary Networks

If a subsidiary cannot query Concheron online, certificate status must
be distributed through an approved signed offline update mechanism.

A trust update may contain:

``` text
trust-update.sec
|
+-- approved issuing certificates
+-- CRL/revocation information
+-- certificate policy version
+-- effective timestamp
+-- update sequence number
+-- Concheron signature
```

The subsidiary must reject tampered or rollback trust updates.

The application should display/record the age of its current
trust/revocation data.

## 19. View Session Protocol

When access is approved:

1.  Generate a cryptographically random view token.
2.  Store only its cryptographic hash where practical.
3.  Generate a separate non-sensitive display code for watermarking.
4.  Bind the session to staff, certificate, document version, and
    expiration.
5.  Return the raw temporary token to the authorized browser session.
6.  Revalidate authorization on page requests.
7.  Terminate on logout, explicit close, timeout, administrative
    revocation, or other policy event.

Exact idle and maximum lifetimes remain configurable policy.

------------------------------------------------------------------------

## 20. CSRF and Web Session Design

State-changing SEC operations require CSRF protection.

The application should use a session-scoped or otherwise multi-tab-safe
CSRF strategy rather than invalidating the only valid token every time a
new tab is opened.

Sensitive operations include:

-   SEC package upload/import.
-   Permission changes.
-   Certificate administration.
-   Trust update import.
-   Key administration.
-   Administrative view-session termination.

Cookies should use appropriate HttpOnly, Secure, and SameSite settings.

## 22. Error Architecture

User-facing errors use safe codes/messages.

Example:

``` text
SEC-IMP-001: The SEC package could not be verified.
SEC-AUTH-003: Staff certificate verification failed.
SEC-VIEW-002: You are not authorized to view this document.
```

Detailed internal diagnostic information belongs in restricted
operational logs.

Do not expose:

-   Key material.
-   Raw OpenSSL/provider errors containing sensitive context.
-   Internal paths unnecessarily.
-   Stack traces.
-   SQL statements.
-   Raw tokens.

------------------------------------------------------------------------

## 23. Rate Limiting and Extraction Resistance

Rate limiting should be applied by staff ID, view session, document, and
possibly client/session context.

The system should detect patterns such as:

-   Excessive page requests.
-   Unreasonable parallel page retrieval.
-   Automated sequential scraping.
-   Repeated invalid page/token requests.

Thresholds must be configurable and tested so normal continuous
scrolling remains responsive.

## 26. Key and Certificate Lifecycle

### USB Credential

``` text
Issue -> Activate -> Use -> Renew/Replace -> Revoke -> Retire
```

### Staff Certificate

``` text
Issue -> Map to Staff -> Authenticate -> Renew/Revoke -> Retire
```

Because Mode A is used, renewal does not require document re-encryption.

### Server Key

``` text
Generate -> Protect -> Activate -> Encrypt/Unwrap -> Rotate -> Retire -> Recover/Destroy
```

Historical keys required for existing documents must not be destroyed
until protected content has been migrated or retention has ended.

## 28. Security Invariants

The implementation must preserve these invariants:

1.  A normal browser never receives the original SEC PDF during viewing.
2.  An SEC package cannot be imported without the intended USB
    private-key operation.
3.  USB and staff private keys are never transmitted to the application
    server as raw private keys.
4.  Imported master PDFs are not retained in plaintext.
5.  Staff certificates do not decrypt documents under Mode A.
6.  Document authorization is checked server-side.
7.  The Concheron extension does not intentionally expose raw
    document/server private keys to ordinary PHP code.
8.  Clean rendered page caches are not publicly addressable.
9.  Watermarks contain no secret authentication material.
10. Security-sensitive failures do not silently fall back to weaker
    processing.

## 32. Architectural Decision Summary

The selected architecture deliberately separates distribution, storage
protection, and user authentication.

**SEC USB credential:** authenticates SEC staff to the central portal
and cryptographically controls the initial downloaded SEC package.

**Subsidiary server key:** protects the imported original document after
successful USB-assisted import.

**Staff certificate --- Mode A:** authenticates individual staff and
contributes to authorization, but never serves as a document-decryption
key.

**Concheron PHP extension:** encapsulates package processing,
cryptographic operations, certificate validation, and protected
key-provider interaction behind a controlled PHP API.

**ZF1 application:** implements business workflow, authorization,
sessions, database state, auditing, import orchestration, and viewer
endpoints.

**Secure viewer:** receives only server-rendered, personalized,
watermarked pages and never the original PDF during normal viewing.

This separation allows Concheron to revoke or replace staff certificates
without re-encrypting SEC documents, rotate server keys independently,
replace lost SEC USB credentials through controlled re-download/recovery
procedures, and evolve cryptographic implementation through versioned
Concheron extension releases.
